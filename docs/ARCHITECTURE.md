# Architecture & conventions

Browser-only tools site. Next.js 16 (App Router, SSG), React 19, Tailwind 4, TypeScript strict.
Every tool and every variant is its own statically generated, indexable page (ru + en).

## Hard rules
1. **Client-only processing.** No server APIs, no third-party network calls, no analytics in tools. Files never leave the browser.
2. **No fake features or claims.** If something can't be done well in the browser, don't ship it. Texts must describe only what the tool really does.
3. **Everything in ru and en.** Correct Russian grammar (cases, plurals via `plural()` from `@/i18n/format`). No English leftovers in RU and vice versa.
4. **Results are live** (no "Calculate" buttons for cheap computations). The initial state of a variant page renders the answer on the server (SSR) so it is in the HTML.
5. **Accessibility:** every input has a label, no `autoFocus`, keyboard reachable, `aria-live="polite"` only on the final result, never on ticking clocks.
6. **Performance:** heavy libraries (pdf, ffmpeg, prettier, wasm codecs…) are loaded with `await import()` inside event handlers or effects, never at module top level of a tool. CPU-heavy work goes to a Web Worker. Revoke object URLs, terminate workers, cancel animation frames on unmount.
7. **Brand** comes only from `src/config/brand.ts` (`BRAND.name`). Never hardcode the site name/domain.
8. **Security headers** (`next.config.ts`): a strict CSP (`connect-src 'self'` — a tool that tries to call another host fails
   loudly), HSTS, no framing. Don't add third-party scripts, fonts or APIs.
9. **Offline.** `public/sw.js` keeps pages and files people have opened (network first for pages, cache first for
   hashed `/_next/static`). It must never cache other origins, POSTs, RSC payloads or anything user-generated; bump
   `VERSION` in it when its caching rules change.
10. **Old devices.** Client JS must parse as ES2021 (Safari 14) and contain **no regex lookbehind** (`(?<=`, `(?<!`) — use
   `src/lib/lookbehind.ts` helpers; `scripts/postbuild.mjs` fails the build otherwise. Browsers without cascade layers
   (iOS < 15.4) get `public/legacy.css`, generated by postbuild from the same CSS; server-rendered pages stay readable
   down to iOS 9, and tools show an "outdated browser" note where the JS can't run.

## Folder layout
```
app/[locale]/…                 generic routes for 1–3 path segments (/[section]/[slug]/[variant] are just segment names)
src/config/brand.ts            site name, domain, verification ids
src/i18n/                      locales, formatting (formatNumber, formatSmart, parseNumber, plural), UI dictionary
src/registry/                  types, section registry, generic tool-section builder
src/sections/<id>/             ONE FOLDER PER SECTION: section.ts, components.ts, tools (*.tsx), engines, data
src/sections/index.ts          list of all sections
src/sections/components.ts     merged map of tool component loaders (source of truth for component ids)
src/sections/tool-components.ts  GENERATED next/dynamic map (scripts/gen-tool-components.mjs, runs in prebuild)
src/site/                      layout, page renderer, blocks, SEO helpers, search
src/ui/                        design-system primitives (link.tsx = next/link without viewport prefetch)
src/lib/                       small shared helpers (cn, clipboard, recent, search)
src/config/redirects.ts        301 map from the previous site's URLs, applied by proxy.ts
scripts/data/gen-*.mjs         build-time data generators (Unicode CLDR etc.) → JSON in src/sections/<id>/data/
scripts/vendor-*.mjs           copy wasm/worker/font assets into public/vendor/ (prebuild)
tests/unit/, tests/e2e/        vitest (registry invariants, engines) and Playwright smoke + axe
```

## How a page is produced
`resolvePage(locale, segments)` finds the section that owns the first segment and calls `SectionDef.resolve()`, which returns a `PageModel` (`src/registry/types.ts`):
title (the complete `<title>`; no brand suffix is appended), h1, description (meta, ≤160 chars), lead (one line with the answer), breadcrumbs, `tool` (component id + serializable props),
`topBlocks` (variant/sibling chips right under the tool), `blocks` (facts, tables, text), `howTo`, `faq`, `related`.
`src/site/page-view.tsx` renders it, `src/site/seo.tsx` builds metadata, canonical, hreflang (ru, en, x-default) and JSON-LD.
The tool itself is rendered by `ToolClient` from the generated `next/dynamic` map: every tool is its own chunk, preloaded
from the HTML of the pages that use it, so shared JS stays at the framework floor.
Sitemaps (`/sitemap.xml` → `/sitemaps/<section>.xml`) and the search index (`/<locale>/search.json`) are generated from `SectionDef.paths()` / `search()`.

## Two ways to write a section
1. **Declarative tools** — `defineToolSection({...tools: ToolDef[]})` from `src/registry/tool-section.ts`.
   **Every tool is a top-level page**: `/{tool slug}` and `/{tool slug}/{variant}`. The slug is globally unique and is the
   English form of the main search query (`microphone-test`, `merge-pdf`, `word-counter`, `percentage-calculator`).
   `slug: ""` puts the tool at `/{section id}` (when the id itself is the query: `timer`, `emoji`).
   The section is a navigation group. Its landing page `/{section id}` is published only when `title` is set and no tool
   has `slug: ""` — set it only if the group name is a real search query; otherwise the group has no page.
   Variants come from `variants.list()` and override the tool's props (e.g. `/timer/5-minutes` → `{ seconds: 300 }`).
2. **Custom SectionDef** — for entity catalogs (emoji, cities, units…): implement `paths()`, `resolve()`, `search()`, `featured()` yourself.
   Reference implementation: `src/sections/convert/section.ts` (hub → quantity pages → pair pages with tables, facts, FAQ).

## Tool design: one focal point
Every tool has one obvious place to look: the primary input and a prominent result (large type, accent where it helps).
Restrained minimalism: at most one quiet row of secondary options; extra data (tables, lists in other units) sits below,
visually quiet; no walls of equal-weight controls, no rows of per-item buttons. If a screen needs explaining, simplify it.

## Tool components
- File `src/sections/<id>/<Name>.tsx`, `"use client"`, **default export**, props `{ locale, ...preset }` (`ToolProps` in `src/sections/types.ts`). Props must be JSON-serializable.
- Register in `src/sections/<id>/components.ts`: `"<id>/<name>": () => import("./Name")` — only dynamic imports in that file.
  Then run `node scripts/gen-tool-components.mjs` (the build does it too; a unit test fails if the generated map is stale).
- Strings: a local `const T = { ru: {...}, en: {...} }` inside the tool file.
- Reference implementation: `src/sections/convert/UnitConverter.tsx`.
- UI primitives (`src/ui`): `Button`, `ButtonLink`, `Field`, `Input` (size sm|md|lg), `Textarea`, `Select`, `Checkbox`, `Switch`, `Slider`, `Segmented`, `Tabs`, `Panel`, `PanelHeader`, `Stat`, `Badge`, `Kbd`, `Notice`, `CopyButton`, `CodeOutput`, `Dropzone`.
  Use them; don't restyle from scratch. `cn()` does NOT merge conflicting Tailwind classes — override with the important suffix (`h-12!`).
- Design tokens (Tailwind utilities): `bg-bg`, `bg-surface`, `bg-surface-2`, `border-line`, `border-line-strong`, `text-fg`, `text-fg-2`, `text-fg-3`, `bg-accent`, `text-accent`, `bg-accent-soft`, `text-accent-fg`, `text-ok|warn|err`, `bg-ok-soft|warn-soft|err-soft`. Radii: 8px fields, 12px panels. No shadows except overlays (`shadow-[var(--shadow-overlay)]`). Component classes: `.control`, `.chip`, `.card`, `.tbl`, `.facts`, `.rows`, `.glyph`, `.prose-lite`, `.tabular`.
- Icons: in client components import from `lucide-react` directly (`import { Copy } from "lucide-react"`). In server code, icons are referenced by lucide name string (`icon: "Ruler"`).
- Numbers: parse user input with `parseNumber()` (accepts "1 000,5" and "1,000.5"), display with `formatNumber()`/`formatSmart()`; never `toFixed` + regex trimming.
- Dates/time: never compute "now" during server render; read the clock in `useEffect` (render a neutral placeholder on the server).
- Randomness: `crypto.getRandomValues` with rejection sampling (no `Math.random` for anything user-facing).
- Links: `import Link from "@/ui/link"` (prefetches on hover/focus only). Long link lists (chips, glyph grids, menus) use plain `<a>`.
- Screens: must work from 320×480 (iPhone 4/SE) to 8K TVs. Above 1600px the root font size grows with the viewport,
  so sizes are in `rem` (no `px` in arbitrary values except hairlines/shadows). Grids without explicit columns shrink
  (`minmax(0,1fr)` by default), long tokens wrap; scrollable tables/lists get `tabIndex={0}`.
- Touch: `Button`, `Segmented` and fields grow to 40–44px on `pointer: coarse`; inputs never use text under 16px on touch
  screens (iOS zooms into them — globals.css enforces it for `text-sm`/`text-xs` fields).
- Icons instead of words where the icon is universal (search, menu, copy, download, close, theme, favourite, share):
  icon-only buttons need `aria-label` and `title`. Keep words where an icon would be a guess.

## SEO requirements for every page
- Title/h1 = what people actually type into a search engine ("Проверка микрофона онлайн", "Таймер на 5 минут"). Never generic group
  names or boilerplate ("… — бесплатные инструменты", "free tools", brand name) — the registry test rejects them.
- Title format: `<exact query> | <second way people search for it>` — "Килограммы в унции | кг в унции конвертер".
  The second half comes from the page title itself (write it with " | ") or from the tool's `seoAlt` (then `keywords`),
  appended by `seoTitleOf` in `src/registry/tool-section.ts` when it fits 60 characters.
- `tests/unit/seo-quality.test.ts` checks every page: title format and length, unique H1, description length, a lead,
  data blocks of its own on every variant/entity page, and no near-copies inside a family (3-word shingles, Jaccard ≤ 0.8).
  `SECTION=<id> npx vitest run tests/unit/seo-quality.test.ts` runs it for one section.
- `related` keys are page paths without locale (`merge-pdf`, `timer/5-minutes`, `convert/km-to-miles`); unresolved keys fail the registry test.
- Unique `title` (≤ 60 chars where possible, key phrase first), unique `description` (120–160 chars, contains concrete numbers/facts), `h1` = main search phrase, `lead` = the direct answer.
- Variant pages: 20–50 chip links to sibling variants (`topBlocks`), a facts block and/or table with data specific to the variant, 2–4 FAQ entries with real answers, breadcrumbs.
- Tool pages: 3–5 `howTo` steps, 3–5 FAQ, `about` text (2–3 short paragraphs, no filler), `related` tools.
- Slugs: lowercase English kebab-case, identical in ru and en.
- Only curated variants with real search demand. No thin pages that differ by one number without useful data.
